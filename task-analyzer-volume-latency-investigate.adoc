= Investigate high latency on a volume in NetApp Console (local deployment)
:hardbreaks:
:nofooter:
:icons: font
:linkattrs:
:imagesdir: ./media/

[.lead]
When application performance degrades, use the Workload Analyzer to identify which part of the I/O path is causing the slowdown. The latency analysis section breaks down response time by delay center so you can distinguish between network issues, data processing overhead, aggregate contention, and other contributors.



== Before you begin

* Ensure NetApp Console (local deployment) has already discovered the volume you want to investigate.
* Identify the approximate time window when the issue occurred so you can select the right analysis range.

.Steps

. In the NetApp Console (local deployment), navigate to *Workload Analyzer*.
+
Alternatively, from the storage inventory, select a volume and select *Analyze*.

. In the *Volume* field, search for and select the volume you want to investigate.

. Set the *Time Range* to cover the period when the performance issue occurred, then select *Analyze*.

. Review the *Event Timeline* section for configuration changes or alerts that correlate with the time when latency increased.
+
The analyzer plots configuration change events (wrench icon) and alert events (warning and critical icons) along the same time axis as the latency chart, making it easy to see whether a change preceded the degradation.

. In the *Latency Analysis* section, open the *View* dropdown and select *By Contribution*.

. Use the metric picker to enable the delay centers you want to examine:
+
* *Network* — time in the client-facing network stack
* *Aggregate Ops* — disk I/O and RAID operations at the aggregate level
* *Data Processing* — inline efficiency operations such as deduplication and compression
* *Cluster Interconnect* — inter-node communication for cross-node data access
* *Cloud Latency* — retrieval from a cloud capacity tier via FabricPool

. Hover over a point on the chart where latency is highest to see each delay center's value and its percentage of total latency.
+
The delay center with the highest contribution usually points to a resource that is in contention. When a shared resource can't keep up with demand, the volumes that use it wait longer for I/O. Reducing the load on that resource, such as moving workloads or adjusting a QoS limit, typically lowers latency.

. Identify the dominant contributor and use the value to determine next steps:
+
* High *Aggregate Ops* latency may indicate disk contention. Check the *Resource Utilization* section to confirm aggregate busy percentage.
* High *Network* latency may indicate NIC saturation or network path issues outside the cluster.
* High *Data Processing* latency may indicate that inline efficiency settings are consuming more CPU than the workload can tolerate. Consider adjusting efficiency settings or QoS.
* High *Cloud Latency* may indicate the workload is frequently accessing cold data on the capacity tier. Consider adjusting the tiering policy.

. If the delay centers don't account for the slowdown, check the *Capacity Analysis* section. When the ONTAP system is more than 85% full, the high utilization can cause performance issues regardless of the delay center breakdown.

. If latency increased immediately after a change event, use the event details and the related charts together to validate the likely cause:
+
* For QoS changes, compare the latency line to the QoS limit lines and review the throughput charts to see whether demand is meeting a policy ceiling.
* For aggregate or volume moves, compare the latency spike to the node and aggregate utilization values shown for the same timeframe.
* For tiering policy changes, review the cloud latency contribution to determine whether cold-data access increased after the change.

.After you finish

If a configuration or placement issue caused the problem and Console (local deployment) can resolve it, the alert associated with the volume may offer a Fix-It option. See link:task-remediation-guided.html[Remediate with guided steps]. Refer to link:reference-workload-analyzer-metrics.html[Workload Analyzer metrics reference] if you need detailed descriptions of QoS limit lines, resource utilization indicators, or forecast behavior while you investigate.
